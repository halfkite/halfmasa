# 自动进食等待回执期间取消导致崩溃

本修复由 Minecraft 26.3 基线同步到全部支持版本：1.21.1、1.21.3、1.21.4、
1.21.5、1.21.8、1.21.10、1.21.11、26.1.2、26.2、26.3。

## 表象与根因

异常为 `Inventory.getItem(-1)`，调用来自 `AutoEatService.onClientTick` 的
`WAIT_SILENT` 分支。`activeSlot` 的 `-1` 是 HalfMasa 自己的“无活动槽位”标记，
不能直接交给原版背包读取。

`cancel()` 为避免已发送的服务端进食事务被再次执行，特意保留 `WAIT_SILENT`。
但随后调用的 `finishSelection()` 同时将 `activeSlot` 清为 `-1`，使状态仍表示
存在未完成请求，而请求依赖的槽位已被丢弃。修改设置、手动操作或来源切换均可能
进入该路径，不需要假定玩家正在频繁开关容器。

此外，关闭功能后的提前返回会阻止请求结算；不确定超时也会每 Tick 重复发出提示。

## 修复规则

- 等待回执期间，`finishSelection()` 不释放请求拥有的槽位及选择记录。
- 取消只阻止后续进食，不假定已经发出的服务端请求能被撤销。
- 即使主开关关闭或玩家正在手动操作，仍处理已有请求的回执和权威背包更新。
- `OK` 回执和对应背包确认均完成后，退出等待状态，再清理槽位。
- 明确失败的回执允许退出等待并清理；未确定结果的超时保留原请求，不产生新请求号，
  不回退到普通使用，且只提示一次。
- 退出世界仍同时清理状态、请求及槽位，避免跨会话复用。

没有在越界读取处吞异常，也没有用“槽位为负则返回”将事务永远留在失效状态。

## 验证方式

`scripts/python/run_auto_eat_smoke.py` 支持额外参数：

`--jvm-arg=-Dhalfmasa.eat.silentCancelRegression=true`

该场景使用真实生存玩家和真实服务端静默进食请求，并延迟回执及背包包：

1. 在 10 号物品栏槽发出静默进食请求。
2. 等待期间修改设置、模拟攻击输入、切换食物来源、关闭功能及触发超时。
3. 检查活动槽位和请求号保留，普通使用请求数不增加。
4. 先恢复回执，确认仍在等待背包更新。
5. 再恢复背包更新，确认仅消费一次、正确退出等待并清理槽位。
6. 保持开关关闭，确认不会继续进食；退出世界检查会话清理。

不带此参数时运行原有自动进食完整回归，覆盖普通食用、物品栏交换与归还、
静默食用、死亡与退出世界；安装 QuickShulker 时还覆盖容器取食及剩余食物归还。

跨版本检查使用 `scripts/python/run_compat_fixes_smoke.py`，逐版运行真实客户端及
单人服务端，验证取消、来源切换、关闭功能、超时与延迟同步，并检查 Conflux Map 列表和落点。

实机测试采用 `-Xint`，沿用本机既有的测试环境设置；这不代表修复了 Java 原生编译进程退出问题。
